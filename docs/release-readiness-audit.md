# KPL Intelligence 上线就绪审计

> 审计日期：2026-10-04（按本次工作区实际日期记录）  
> 范围：静态代码与配置检查、文档核对、无外部服务的 TypeScript 类型检查。未连接/写入数据库，未运行浏览器、部署、采集、LLM 或推送。  
> 结论：**目前不建议直接公开推广上线**。核心赛事数据与内容站基础已经存在，但 AI 问答产品闭环尚未实现，公开服务安全配置和信源许可边界仍需上线前明确；部署文档与 KPL 仓库身份也有明显漂移。

## 1. 执行摘要

项目具备可继续产品化的基础：KPL 行业包、赛事数据适配器、战队/选手/比赛页面、赛事数据库迁移、AIHOT 的新闻编辑/归组/发布机制、站点 API、Docker 构建和 SEO 公共模块均可在代码中找到。`npm run typecheck` 本次通过。

但不能据此判定“生产可用”。本次检查发现：

- 数据库迁移中创建了问答和向量检索表，但代码中未发现 QA 模块、问答 API 或 `/ask` 页面；交接文档也把 Phase 3c 标为 0%。这与“AI 智能检索平台”的核心定位存在差距。
- `.env.example` 将采集与模型调用默认写为 `true`，而仓库 Agent 指引要求安全阀默认关闭。部署指引又建议从 AIHOT 上游仓库克隆，容易误部署错误产品/种子。
- 官方公众号信源设置 `site_fulltext: true`；另有自建公众号抓取桥返回 RSS `content:encoded` 正文。公开全文授权与微信生态抓取稳定性未在现有材料中得到验证。
- 站点含有赛事、战队、选手 SEO 元信息，但赛事实体页没有全部进入 sitemap 的证据；需要核验发布出口和爬虫收录效果。
- 当前 Node 为 v25.9.0，而项目声明要求 `>=24.11`；版本满足下限但与生产 Docker Node 24 不完全一致，建议验证固定运行时版本。

## 4. 问题清单

### P0 — 上线阻断

#### P0.1 核心 AI 问答闭环未落地
- **证据**：`0055_kpl_kb_search.sql` 创建 `chunks`、`qa_queries` 等表，但 `packages/backend/src/kb/` 只有读写实体模块；API route 列表无 QA 路由，Web routes 无 `/ask`。交接文档 §3 将 Phase 3c 标为 0%。
- **用户影响**：产品定位中的“AI KPL 问答/智能检索”无法兑现；向量表本身不会自动产生可用问答。
- **建议**：首发前明确产品是否以问答为核心。若是，实施最小可用 RAG：结构化查询 + 关键词检索起步、明确引用、来源链接、拒答/降级、限流与模型预算；向量召回可在测试集证明增益后再接入。
- **验收标准**：覆盖赛果、H2H、选手/战队统计、新闻类问题的离线用例；答案数字和实体均可追溯到数据/引用；未知问题能拒答；模型关闭或额度耗尽时站点仍可正常访问并展示检索结果/提示；端到端测试不使用真实供应商。

#### P0.2 安全阀默认值与部署操作需收敛
- **证据**：`AGENTS.md` 明确开发环境采集和模型调用默认保持关闭；`.env.example` 当前为 `COLLECT_ENABLED=true`、`MODEL_CALLS_ENABLED=true`。`docs/deploy.md` 又指导照示例配置上线。
- **用户影响**：开发/测试环境可能意外抓取外部源并产生模型费用；配置示例和代码约定冲突。
- **建议**：产品负责人确认生产启用步骤；示例默认关闭，生产 runbook 要求操作者显式启用并设置预算/来源范围。核对 Compose 是否只在显式设置时启动这些能力。
- **验收标准**：缺省配置不会启动采集、模型或推送；生产启用步骤有显式检查清单；集成测试断言默认关闭。

#### P0.3 内容全文与图像展示许可边界未确认
- **证据**：`industry/sources.json` 官方公众号信源 `site_fulltext: true`；`docs/wechat2rss.md` 描述输出 `content:encoded` 全文及修复微信图片防盗链；文档没有展示授权证据。
- **用户影响**：可能产生版权、平台条款或内容再发布风险；“公开可访问”不等于授权转载。
- **建议**：未获得明确许可前，对公众号和第三方源使用标题、短摘要、来源署名、原文链接；全文仅内部处理或按授权展示。逐类确认图片代理和缓存策略。
- **验收标准**：建立信源许可台账（来源、可展示字段、全文/图片许可、确认人、日期）；无许可来源默认不公开全文和图片；页面及 RSS/API 遵循同一策略。

### P1 — 首发前强烈建议

#### P1.1 README 与部署文档仍像 AIHOT 模板
- **证据**：`docs/deploy.md` clone 示例指向 `KKKKhazix/AIHOT.git`、目录名 `myhot`；产品 README 当前仍使用 AIHOT 品牌内容（此前检查确认）。
- **影响**：运营者可能部署错误仓库；访客和贡献者无法理解 KPL 产品、数据来源和启动方式。
- **建议**：重写产品 README 和部署文档，明确 KPL 产品名、仓库地址、环境变量、安全阀、数据源、许可、备份恢复、生产升级流程；清除 AIHOT 作为产品品牌的残留，但保留必要的上游致谢/许可证声明。
- **验收**：新手按文档从干净环境部署成功；文档不再把上游仓库当本站入口；品牌和许可证表述经过负责人确认。

#### P1.2 公众号桥与公开 API 尚未做滥用面审查
- **证据**：未提交 `wechat-feed.ts` 暴露 `/api/wechat/search`、`/api/wechat/preview` 与支持 `force` 参数的公开 RSS 端点；`force` 可要求绕过缓存的行为需要确认是否会直接触发上游请求。查询参数无可见长度/频率限制。Fastify 全局设置 `trustProxy: true`，与 `.env.example` 中 `TRUST_PROXY=false` 的说明不一致。
- **影响**：可能被用于上游请求放大、公众号枚举、费用/封禁风险；代理头信任策略可能影响客户端 IP 限流与审计。
- **建议**：检查 `wechatBridge` 的缓存、单飞、并发、限流、错误语义和 force 保护；限定查询长度、账户数量和请求频率；统一代理信任配置并审查 IP 获取路径。保持当前工作区改动不变，先提出补丁再经用户确认。
- **验收**：自动化测试覆盖并发去重、缓存绕过授权/限频、错误时不泄露内部信息、恶意参数、代理伪造场景；滥用无法显著放大上游请求。

#### P1.3 赛事数据完整性和来源状态面向用户不透明
- **证据**：赛事页面描述数据来自官方赛事接口；本次没有访问数据库/上游验证历史覆盖、更新时间和补赛/修正处理。交接文档提及官方接口无正式契约。
- **影响**：数据过期或官方接口变更时，用户可能将旧赛程/错误赛果当作事实。
- **建议**：公开数据截至时间、赛事数据来源与异常说明；运营后台监控最近成功抓取、失败率、积压；关键比赛支持修正审计记录；对上游 schema 变化做告警。
- **验收**：异常/过期场景可见；比赛详情提供来源与更新时间；worker/采集失败告警经测试验证；修正有来源和操作者记录。

#### P1.4 部署与恢复未实测
- **证据**：Dockerfile 包含构建流程，部署文档有 Compose/Supabase 说明；本次未运行 Compose、迁移或恢复。交接文档要求关闭 Supabase Data API，安全状态未核验。
- **影响**：容器启动、数据库连接、任务调度、备份恢复和回滚在真实环境可能失败；数据库暴露面未核验。
- **建议**：在隔离 staging 项目验证全链路构建/启动/健康检查/迁移/备份恢复；确认 Supabase RLS/Data API 暴露策略和最小权限；制定回滚前提。
- **验收**：无生产数据的 staging 完成部署与恢复演练；健康检查涵盖 API/DB/worker；备份恢复有时间目标记录；Data API 与凭据安全经负责人确认。

#### P1.5 Node 运行时版本不一致
- **证据**：本机 Node `v25.9.0`；`package.json` 要求 `>=24.11`；Dockerfile 使用 `node:24-trixie-slim`。
- **影响**：本次类型检查虽通过，但本机测试结果未完全代表生产运行时。
- **建议**：用与 Docker 一致的 Node 24.x LTS 版本执行构建和测试，并明确版本管理文件/CI 版本。
- **验收**：CI 和发布镜像采用受支持且一致的 Node 24 版本；typecheck、web build、测试在该版本全绿。

#### P1.6 KPL 实体页索引收录需验收
- **证据**：已有 sitemap 与通用 canonical/OG 实现；本次未证实 KPL 的比赛、战队、选手路由全部纳入 sitemap，也未验证 robots、站点地图内容或生产域名链接。
- **影响**：推广分享和搜索引擎发现效率低，或错误收录空页面。
- **建议**：对高价值、数据完整页面添加可索引规则；空/薄页面 noindex；核对 sitemap URL、canonical、OG 卡片和结构化数据。
- **验收**：staging 生成的 sitemap 包含预期 KPL URL；页面 canonical/OG 指向生产域名；缺失实体返回正确 404/noindex。

## 7. 最小首发路线图

### 阶段 0：产品范围和风险收口
- **交付**：确认 AI 问答是否首发；确认品牌、信源许可、全文/图片策略；关闭默认安全阀；修订 README/部署文档。
- **验收**：运营者不会误部署 AIHOT；默认配置不产生外部采集/模型调用；来源展示策略有书面记录。
- **风险/回滚**：只改文档和默认配置时回滚容易；生产启用开关前核对预算和来源名单。

### 阶段 1：可用的核心用户任务
- **交付**：先把赛程/比分/战队/选手/新闻主路径和更新时间、来源标注、空/错状态打磨完整；若问答必需，再单独实现最小 RAG 闭环。
- **验收**：关键用户任务有端到端测试；无数据时行为合理；引用可打开且能核验；服务降级不影响静态赛事浏览。
- **风险/回滚**：问答采用独立 API/开关，故障时可关闭，不影响内容站。

### 阶段 2：生产安全与运行验证
- **交付**：Node 24 CI 验证、staging Compose 部署、数据库安全配置、告警/日志、备份恢复演练、来源失效降级。
- **验收**：staging 部署和恢复均成功；安全检查清单签字；关键服务健康状态可观测。
- **风险/回滚**：迁移前备份；生产升级遵循停 worker/API、迁移、启动、健康确认顺序。

### 阶段 3：小范围发布与推广
- **交付**：品牌化首页、产品说明/来源声明、分享卡片、反馈与纠错入口、发布说明；先邀请小范围 KPL 用户试用。
- **验收**：试用者能完成目标任务；收集并分类真实错误；没有未处理的 P0；运营能响应来源故障和纠错。
- **风险/回滚**：先灰度域名/限量开放；准备关闭采集、问答或回退上一镜像的操作手册。
